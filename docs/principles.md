# XMUHub 设计原则

这份文档解释 [AGENTS.md](../AGENTS.md) 里那些硬性规则**为什么**存在。给参与开发的同学和他们用的 AI 助手看。

## 为什么服务器不能经手资料文件

XMUHub 跑在一台很小的阿里云服务器上：

| 资源 | 情况 |
|---|---|
| 出口带宽 | 很小，按流量 / 带宽计费 |
| 磁盘 | 只剩几 GB |
| 内存 | 整机 3.5 GB，和其他服务共用；XMUHub 服务进程上限 400 MB |
| CPU | 2 核 |

几百份资料加起来有几 GB，单个文件最大几百 MB。只要服务器替用户下载或转发一次文件，就要占用同样多的出口流量；如果还把文件读进内存，几个人同时预览大文件就能让服务进程超过 400 MB 被系统杀掉，整个网站随之掉线。

所以整个系统是这样设计的：

```
上传：浏览器 ──(流式中转，不落盘，有上限)──▶ GitHub Releases
下载 / 预览：浏览器 ──▶ 国内 GitHub 镜像 ──▶ GitHub Releases
服务器：只存数据库（分类、资料信息、账号……），只返回 JSON 和镜像链接
缩略图：GitHub Actions 生成 ──▶ GitHub Releases
```

服务器在整个流程里只负责「告诉浏览器去哪里拿」，从不自己去拿。

## 镜像为什么会「失败」，该怎么修

下载和预览依赖公共的 ghproxy 类镜像（`gh-proxy.com`、`ghfast.top`……）。服务器每 15 分钟通过每个镜像下载一个 256 KB 的探针文件，给镜像测速排序：

- **下载**可以用任何镜像：浏览器直接跳转过去。
- **在线预览**需要网页用 `fetch` 读文件内容，所以只能用会发 `Access-Control-Allow-Origin` 头的镜像（「CORS 镜像」）。

常见的失败原因：

1. **镜像对我们服务器的 IP 限流（HTTP 429）或超时**。这只说明服务器自己访问不了，不代表用户访问不了——用户浏览器用的是自己的 IP。探测把这类「软失败」的 CORS 镜像继续留在预览列表里（排在后面），浏览器 8 秒连不上就自动换下一个。
2. **镜像下线或开始返回错误内容**。从 `DEFAULT_MIRRORS` / `KNOWN_CORS` 里删掉，换新的。
3. **所有 CORS 镜像都不可用**。页面会提示「暂时没有支持在线预览的下载线路，请稍后再试或直接下载」。这是可以接受的降级结果。

**新镜像加入前要验证**（在服务器上执行，因为要看国内的访问情况）：

```bash
F='https://github.com/vintces-private/<仓库>/releases/download/<tag>/<文件>'
curl -sL -H 'Origin: https://xmu.vintces.icu' -D - "https://<镜像>/$F" -o /tmp/x | grep -i access-control-allow-origin
sha256sum /tmp/x   # 必须和数据库里记录的 sha256 一致
```

### 反面例子（已回退）

2026-09-25 有人为了修「预览打不开」，加了 `/api/resources/{id}/preview/{index}`：镜像都失败时由服务器下载整个文件（最多 80 MB）、放进内存、再发给浏览器。当时预览打不开的真正原因是：预览用的三个 CORS 镜像对服务器 IP 返回 429 或超时，被探测全部剔除，预览列表变空。正确的修法是修探测逻辑 + 补充新的 CORS 镜像，而不是让服务器兜底。这个接口已经删除，以后不要再加回来。

## 其他原则

- **数据库**：redb + postcard。已有记录结构不改字段（改了旧数据会读不出来），新功能加新表。改结构或批量改数据前先备份线上数据库。
- **前端**：纯静态 ES module，没有构建步骤。第三方库放在 `web/vendor/<名字>-<版本>/`，固定版本。
- **密钥**：只在 `.secrets/`，不进仓库。管理员名单只在 `.secrets/admins.txt`。
- **部署**：`pwsh scripts/sync.ps1`。Rust 改了必须重新编译完整部署，不要只发网页。
